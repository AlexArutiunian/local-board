# AGENTS.md

Этот файл задаёт правила работы coding-агентов в `local-board`. README описывает продукт и запуск для человека; здесь находятся инженерные ограничения, которые агент обязан соблюдать при каждом изменении.

## 1. Сначала пойми продукт

`local-board` — не одиночный canvas и не demo-форма. Это **локальная совместная realtime-доска**.

Обязательный core flow:

```text
Apple Pencil / mouse on client A
→ local optimistic rendering
→ realtime network event
→ authoritative server state
→ live rendering on clients B/C/...
→ durable local persistence
```

Изменение считается корректным только если не ломает этот end-to-end путь.

Перед работой прочитай в таком порядке:

1. текущую задачу пользователя;
2. `README.md`;
3. `docs/architecture.md`;
4. релевантные модули и тесты;
5. этот файл.

Если фактический код расходится с документацией, не маскируй расхождение: исправь код и/или документацию в том же изменении.

## 2. Делай сразу чистый полезный срез

Не плодить `v2`, `v3`, `new`, `final`, `backup`, `old`, `legacy`, `test2` и похожие параллельные реализации.

Не делать «MVP у MVP» и цепочку временных файлов. Если новый путь заменяет старый, **перенеси нужное и удали старый путь в том же изменении**, когда это безопасно.

Предпочтение:

```text
маленький законченный end-to-end feature
>
несколько полуготовых реализаций и архивный код
```

## 3. Структура репозитория — часть качества

Корень репозитория должен оставаться коротким и понятным. Не складывай рабочий код в корень без причины.

Целевая структура:

```text
.
├── README.md
├── AGENTS.md
├── pyproject.toml
├── docs/
├── scripts/
├── src/local_board/
└── tests/
```

Правила:

- backend-код живёт в `src/local_board/`;
- web UI живёт в `src/local_board/web/`;
- документация архитектуры — в `docs/`;
- команды/служебные скрипты — в `scripts/`;
- тесты зеркалят ответственности модулей в `tests/`;
- runtime/user data не хранить в git checkout по умолчанию;
- временные эксперименты не коммитить, если они не стали частью продукта или тестов.

Не создавать бессмысленные глубокие пути и каталоги из одного случайного файла. Любой новый каталог должен отражать устойчивую ответственность.

## 4. Не накапливай legacy debt

После изменения не должны оставаться два конкурирующих способа делать одно и то же без явной причины.

Запрещённые привычки:

- закомментированные старые реализации;
- `*_old.py`, `*_backup.js`, `app_new.js`;
- мёртвые endpoints и неиспользуемые feature flags;
- дублированный protocol/state logic в нескольких местах;
- README с командами для уже удалённой архитектуры;
- совместное существование нового модуля и старого монолитного файла «на всякий случай».

Если refactor завершён — удали заменённый код. Git уже является историей проекта.

## 5. Размер и ответственность модулей

Не складывай весь проект в `app.py` или один гигантский `app.js`.

Разделяй по ответственности, а не ради количества файлов. Например:

- transport / WebSocket;
- protocol validation;
- room/state;
- persistence;
- canvas rendering;
- pointer input;
- client synchronization.

Ориентир: если файл стабильно уходит за ~300–400 строк и в нём уже несколько независимых причин для изменения, это сигнал разделить его. Это не механический лимит: маленький связный модуль лучше искусственного дробления.

Одна функция должна иметь одну понятную ответственность. Избегай hidden global state и clever one-liners.

## 6. Realtime — сервер авторитетен, UI оптимистичен

Для shared state сервер является authoritative source of truth.

При этом рисование должно ощущаться локальным:

- точка Pencil сначала отображается на текущем клиенте;
- сеть не должна быть в critical path визуального отклика;
- остальные клиенты получают mutation в realtime;
- reconnect начинается со snapshot/resync;
- непринятые операции нельзя молча терять;
- mutation должна иметь стабильный идентификатор (`op_id`) и быть безопасной к retry;
- повторно доставленная операция не должна применяться дважды.

Viewport (`pan/zoom`) по умолчанию является локальным состоянием клиента. Не синхронизируй камеру всех участников, если это специально не требуется.

## 7. iPad / Apple Pencil — first-class client

Любое изменение canvas/input проверяй мысленно и тестами против Safari/iPad semantics.

Обязательные принципы:

- использовать Pointer Events, а не отдельную несовместимую ветку mouse-only;
- `pointerType === "pen"` — основной путь рукописного ввода;
- использовать pressure, когда он доступен, но иметь нормальный fallback;
- touch на canvas по умолчанию нужен для pan/pinch, чтобы палец не оставлял случайные чернила;
- не допускать browser scroll/zoom жестов поверх рабочего canvas;
- controls должны иметь touch-friendly hit area;
- toolbar не должен перекрывать критическую часть canvas на iPad.

Не добавляй UI-framework только ради формы вокруг canvas. Здесь frontend — core deliverable.

## 8. Dependencies, templates и лицензии

Перед добавлением стороннего template, component library, asset или существенного copied code **обязательно проверь текущую лицензию**.

### Шаблоны и копируемые assets/code

Можно напрямую брать/адаптировать шаблон или asset только если лицензия однозначно позволяет это **без обязательной атрибуции автору и без пользовательского branding/footer**. Предпочтение:

- public domain;
- CC0;
- Unlicense;
- другой явно эквивалентный режим после проверки текста лицензии.

Не считать «лежит на GitHub» разрешением на копирование.

### Зависимости

Обычная библиотека-зависимость допустима только после проверки её лицензии и production-условий. Нельзя добавлять зависимость, которая:

- требует production license key для нашего сценария;
- навязывает watermark / `Made with ...` / footer branding;
- запрещает нужный режим self-hosting;
- неожиданно переводит весь проект под copyleft-обязательства.

Если permissive license требует сохранить copyright/license notice, это юридическое требование нельзя игнорировать. Либо корректно выполняй его вне пользовательского UI, либо выбери альтернативу с более подходящими условиями.

**Не копировать AGPL/GPL/copyleft whiteboard-код в этот проект без явного решения владельца проекта.** Изучать архитектурные идеи и независимо реализовывать общий паттерн можно.

Для этого проекта не использовать Gradio/Streamlit как оболочку canvas: они не решают core interaction model и создают ненужный framework shell.

## 9. UI без чужого branding

Интерфейс должен выглядеть как самостоятельный `Local Board`.

Не добавлять:

- footer «Powered by ...»;
- ссылки на UI-framework в пользовательском интерфейсе;
- watermark сторонней библиотеки;
- debug panels на основном экране;
- framework-default theme, если она визуально выдаёт шаблон вместо продукта.

Если сторонняя лицензия требует пользовательскую атрибуцию, сначала найди альтернативу; не прячь обязательную атрибуцию CSS-ом.

## 10. Persistence и данные

Пользовательские доски — runtime data, а не source code.

По умолчанию храни их вне репозитория через XDG-compatible путь (`~/.local/share/local-board/...`) или явно заданный `LOCAL_BOARD_DATA_DIR`.

Запись должна быть атомарной. Не оставлять полу-записанный JSON при нормальном процессе сохранения.

Формат persisted state должен иметь version и быть достаточно явным для будущей миграции.

## 11. Protocol discipline

Realtime protocol — публичный контракт между frontend и backend.

При изменении protocol:

1. обнови validation;
2. обнови server apply/broadcast;
3. обнови client apply/send;
4. обнови tests;
5. обнови `docs/architecture.md`, если меняется семантика.

Не передавай произвольный client payload напрямую в persisted state без validation.

Ошибочный event должен приводить к controlled error, а не к падению всей комнаты.

## 12. Надёжность без архитектурного театра

Текущий deployment — один Linux-хост и несколько клиентов в LAN. Не добавляй Redis, Kafka, Kubernetes, CRDT или БД «для солидности», пока они не решают реальную текущую проблему.

Но локальная простота не оправдывает потерю данных или гонки. Где нужно, обеспечь:

- idempotency;
- reconnect;
- snapshot/resync;
- atomic persistence;
- bounded payloads;
- clear connection status;
- controlled failure.

Если появится требование нескольких backend-процессов/серверов, сначала измени architecture doc, потому что текущий in-memory `BoardRoom` предполагает один authoritative process.

## 13. Тесты и проверка

Минимум для backend feature:

- protocol validation happy path;
- malformed input / failure path;
- persistence roundtrip;
- state mutation semantics, если меняются.

Для realtime изменений по возможности делай integration smoke-test с двумя WebSocket clients: событие от A должно прийти B, а новый client C должен получить тот же state в snapshot.

Для frontend перед завершением проверь:

- JS syntax;
- resize canvas;
- Pencil/mouse path;
- touch pan/pinch;
- remote event rendering;
- reconnect state;
- toolbar на узком viewport.

Не объявляй проверку выполненной, если фактически её не запускал.

## 14. Documentation и commands

README должен описывать **текущий** способ запуска. Не сохраняй инструкции к удалённой версии.

После структурных изменений проверь:

- команды clone/install/run;
- реальные пути файлов;
- env variables;
- data location;
- architecture diagram;
- список фактически реализованных возможностей.

## 15. Git hygiene

Коммиты должны описывать законченное изменение, а не случайный промежуточный state.

Перед завершением:

- нет ли секретов и локальных данных;
- нет ли generated мусора;
- нет ли архивных копий;
- нет ли неиспользуемого старого кода;
- README/architecture соответствуют дереву;
- tests/syntax checks пройдены.

Git хранит историю. Репозиторий должен хранить **текущую архитектуру**, а не кладбище прошлых попыток.
